# Hoops (ScoreTrack) — UNA Watch app

Basketball shooting tracker for the UNA Watch, built on the UNA SDK v1.6.0-rc1 (checkout at ~/una-sdk) with the
**LVGL** GUI (no TouchGFX — the developer is on Ubuntu, where TouchGFX Designer
doesn't exist). Scaffolded from the SDK tutorial `Docs/Tutorials/Buttons` (LVGL variant) with fonts from
`Examples/Apps/RunLVGL`; RunLVGL remains the reference for the Model + ScreenManager + Theme pattern.

Competition: UNA App Competition, deadline **30 Oct 2026, 16:00 UK**. Judged on
Usefulness, Originality, UX/UI (10 pts each). Must be published on
apps.unawatch.com and submitted via the form. A table-tennis app may follow as a
second entry (max 2 per person) — keep the scoring engine reusable.

## Architecture (as built)

Two processes, as every UNA app:

- **Service** (`Software/Libs/Sources/Service.cpp`, `Storage.cpp`): owns the session engine, all
  statistics, storage, settings (`settings.bin`, applied to haptics, backlight and HR), haptics (vibro +
  backlight), heart rate and wrist-raise sensors. One `onSecond()` per wall-clock second drives timers;
  `current.bin` is saved after every input and every 5 running seconds. Once a minute while the GUI runs it
  re-sends LOCAL_TIME if the local date changed.
- **GUI** (`Software/Apps/LVGL-GUI/gui/`): `Model` (latest copy of what the service sent — snapshot, settings,
  paged history, spot records — + navigation memory), `ScreenManager`, `Theme` (runtime palette, dark/light),
  widgets (`ListMenu`, `Ring`, `Court`, `Hints`, `KeyInput`, `Toast`) and one class per screen. It computes no
  statistics and touches no files.
- **Engine** (`Software/Libs/score/`): plain C++17, no SDK/GUI dependencies, unit-tested on the host —
  `Spots`, `Session` (≤ 400 shots), `Workout` (+ 15 presets from `presets.json`, ≤ 8 steps, ≤ 10 user
  workouts; `Presets.hpp`/`Presets.cpp` are generated by `tools/gen_presets.py`, `PresetsTable.hpp` holds the
  `step()` helper and the `kPresets[kPresetCount]` declaration), `SessionEngine`
  (open/workout sessions, rest, undo, pause, crash `restore()`, `currentStreak()` (trailing makes, capped at
  255), `Snapshot` incl. `streak`), `Stats`, `History` (`SessionIndex`, 50 rows, trend of 5, per-spot
  `last[13]`/`best[13]` records via `recordSpots()`), `Settings` (defaults, `valid()`), `Serializer`.
- **IPC** (`Software/Libs/Header/Commands.hpp`): padding-free POD messages. `0x01xx` GUI → Service
  (START_OPEN 0x0101 … GET_HISTORY 0x0110, SET_SETTINGS 0x0111, GET_SPOT_STATS 0x0112, CLEAR_HISTORY 0x0113,
  GET_SETTINGS 0x0114, RESET_WORKOUTS 0x0115), `0x02xx` Service → GUI (SNAPSHOT, UNDO_RESULT, STEP_DONE, WORKOUT_ITEM, RESULTS,
  HISTORY, LOCAL_TIME, SAVED, WORKOUT_SAVED 0x0209, SETTINGS 0x020A, SPOT_STATS 0x020B). A RESULTS reply with
  `sessionId 0` means "none"; `GET_RESULTS{0}` = the session just ended. History is **pull-based**:
  `GET_HISTORY{offset, seq, pad[2]}` → exactly one HISTORY page `{total, offset, count, seq, items[5]}` (rows
  offset.. newest first, `seq` echoed; count 0 past the end, `{0,0,0}` for an empty index).
  `Model::requestHistory(all)` starts a stream (`++seq`, offset 0) and drops pages with another seq or offset;
  with `all` it asks for the next page from each one that arrives (one HISTORY in flight). Home, Settings and
  Results-after-a-session ask for the first page only (it carries `total`); History and Results-from-History
  pull all of it. History asks for the user workouts first and starts its stream from `onWorkouts()`;
  Settings asks for its first page first and, if the Model holds no list, the workouts from `onHistory()`.
  SETTINGS (`score::Settings`) goes out on GUI start before LOCAL_TIME and the first snapshot, after every
  SET_SETTINGS (an invalid one is ignored and answered with the settings in force) and, with LOCAL_TIME, in
  answer to GET_SETTINGS (the Model sends it on resume while it has no SETTINGS; Settings rows read "Loading…"
  and SELECT does nothing until then). SPOT_STATS = `SpotStat last[13], best[13]`. CLEAR_HISTORY writes the
  empty index first, then removes the indexed `.bin`/`.csv` files, then sends SPOT_STATS; the Model follows it
  with a GET_HISTORY (the empty page). SAVE_WORKOUT is answered by WORKOUT_SAVED alone; the Model then sends
  GET_WORKOUTS (at most one list in flight: a repeat within 1 s is skipped). RESET_WORKOUTS (empty) empties
  the `WorkoutStore` and saves `workouts.bin` — refused (logged, no change) while a user workout (id ≥ 100)
  runs; the presets are code and stay — and is answered with the workout list alone (one `WORKOUT_ITEM{0,0}`
  when empty); `Model::resetWorkouts()` counts that reply as the list in flight.
- **Storage** (app directory; simulator: `Software/Output/`). Every `.bin` file = 12-byte header {magic, size,
  FNV-1a checksum} + the raw POD:
  - `workouts.bin` ('HWK1', `WorkoutStore`), `settings.bin` ('HST1', `score::Settings`, 12 B; missing or
    invalid = defaults, written only when the user changes a setting) and `sessions/index.bin` ('HIX2',
    `SessionIndex` + the per-spot records; an old 'HIX1' file fails to decode → empty index, its session files
    stay on disk unindexed): written as `<path>.tmp` then renamed over the target; a lone `.tmp` is recovered
    on load.
  - `current.bin` ('HSS1', `Session`): the running session, for crash resume (restored → Paused, `kResumable`);
    written atomically like the others. End & save: session file → index row + spot records (in memory) → CSV
    → index → evicted files (only after the index is written) → remove current.bin, so a crash at any point
    loses nothing and no index on flash lists a removed file (a current.bin whose id is already indexed is
    dropped on start). A restored workout session whose step no longer fits the (edited) workout continues
    as an open session.
  - `sessions/<id>.bin` ('HSS1'): one per saved session; evicted with its index row (oldest beyond 50).
  - `sessions/<id>.csv` (plain text, no header block; only with the CSV export setting on): written on End &
    save after the session file and the in-memory index row, before `index.bin` (a crash between leaves at worst
    an orphan CSV). Header `session_id,date,workout,shot,spot,category,made,t_s`, one row per shot, e.g.
    `1791651056,2026-10-10,Game Shots S,1,3PT · Top,3PT,1,12` (`workout` = preset/user name or `Open`, a `,` in
    it becomes a space; `spot` keeps the UTF-8 middle dot; `t_s` = seconds since the session start). Lines are
    buffered in `Storage::mBuf` (≈ 10 writes for 400 shots); a failed write logs a WARNING and removes the torn
    file, the session is still indexed. Removed with its session (eviction, Clear history). On the watch:
    `Apps/Hoops/sessions/` over USB mass storage. Nothing reads CSVs back.
- **Screens** (`ScreenId` order): Home, SpotPicker, Workouts, WorkoutPreview, StepBuilder, Active (open and
  workout mode, undo / streak / target toasts), Rest (also the workout-done summary), Pause, Results (4 pages:
  court, categories, highlights, trend), History (every indexed session, up to 50, rows appear as pages
  arrive), Settings.
- LVGL pool `LV_MEM_SIZE` 56 KB (both CMake files): peak 23 640 B ≈ 23.1 KB in the full self-test walk
  (SpotPicker → Active change-spot switch). RAM (`arm-none-eabi-size`): GUI data+bss 162 044 B ≈ 158 KB of
  600 KB, service 20 036 B ≈ 20 KB of 500 KB; `.uapp` 311 316 B (0.2.0 branch build).

## Hardware & SDK facts (SDK v1.6.0-rc1 (checkout at ~/una-sdk); online docs are v1.5.0)

- Display: 1.2" round MIP LCD, 240×240, 64 colours (ABGR2222), LED backlight, no touch.
- Buttons: L1 top-left (UP), L2 bottom-left (DOWN), R1 top-right (SELECT/START/STOP), R2 bottom-right (BACK).
  LVGL: key events via `LV_EVENT_KEY` → `Screen::onKey(code)`, one code per 100 ms frame. The kernel sends PRESS,
  RELEASE and CLICK (only for holds < 500 ms); the simulator sends CLICK before RELEASE, the watch's order is not
  documented, so `KeyInput` does not depend on it: every press ends as exactly one Click or HoldRelease (a short
  RELEASE without CLICK waits `kReleaseGraceMs` = 150 ms, one 100 ms frame plus jitter, for a late CLICK, else
  becomes a HoldRelease via the callback; after a 500 ms Hold the RELEASE is a HoldRelease at once). Screens act on `KeyInput::isActivate()` in `Screen::onAction()`
  (feed() results and callback deliveries alike), so a slow press is never lost and a short one never counts
  twice; screens that navigate on a hold do it on HoldRelease, so the release can't reach the next screen.
- Sensors (`SDK::Sensor::Type`): ACCELEROMETER, GYROSCOPE, FUSION, HEART_RATE, WRIST_MOTION, MOTION_DETECT,
  ACTIVITY_RECOGNITION, GESTURE_RECOGNITION (undocumented), TOUCH_DETECT. `SDK::Sensor::Connection(type, period,
  latency)`; batched `EventData`.
- Feedback: `SDK::Message::RequestVibroPlay` (≤ 4 effects per series here), `RequestBacklightSet`
  {brightness, autoOffTimeoutMs}. Mock FS `rename` is POSIX (overwrites); the watch FS may not — Storage
  removes the target and retries.
- **Service → GUI messages: the GUI queues at most 10 app messages between frames, oldest evicted when full**
  (`GuiCommandProcessor`, `FixedQueue<MessageBase*, 10>`, `$UNA_SDK/Libs/Source/Port/GuiCommandProcessor.cpp`;
  log "Queue for custom messages is full"). The queue is drained once per 100 ms frame, before the keys. Never
  burst: a reply plus whatever else can land in the same frame (the 1 Hz SNAPSHOT while a session runs, other
  requests sent in that frame) must stay ≤ 10. Today: GUI_RUN = SETTINGS + LOCAL_TIME + SNAPSHOT; GET_WORKOUTS =
  ≤ 10 WORKOUT_ITEMs (the largest reply; with the 1 Hz SNAPSHOT it can reach 11 — the Model re-asks once
  for a list with a gap, see Known limitations); everything else is one or two messages; history is pulled page by page.
- Docs: https://www.developers.unawatch.com/sdk-v1.5.0/ (index: genindex.html). Pick pages by title.

## Decided UX (mockups are the source of truth where the spec differs)

- Menus: UP/DOWN scroll, SELECT open/confirm, BACK back. Headers are Regular14 (mockups' 11–13 px).
- Shooting: **SELECT = MAKE** (1 buzz), **BACK = MISS** (2 buzzes), **UP = undo** (3 buzzes + 2 s toast
  "Make removed" / "Miss removed" / "Nothing to undo"), **DOWN = pause**, **hold DOWN (500 ms) = change spot**
  (open session; toast "Release to change spot" while held, picker opens on release; in a workout a hold pauses).
  Setting Hold DOWN = Pause: no hold toast, the HoldRelease of DOWN pauses like a click (open sessions too).
  Shot and undo turn the backlight on only with "Backlight on shot" (default On); step end / rest over / skip /
  target reached / save / wrist raise (during a session) always do; menu navigation does not.
- Haptics (service `haptic(HapticEvent)`, table `kHaptics` in `Service.cpp`; setting Haptics, default Strong):

  | event | Strong | Light |
  |---|---|---|
  | make | SHARP_CLICK_100 | SHARP_TICK_1_100 |
  | miss | SHORT_DOUBLE_CLICK_STRONG_1_100 | SHORT_DOUBLE_SHARP_TICK_1_100 |
  | undo | 3× SHARP_TICK_1_100 | 3× SHARP_TICK_1_100 |
  | step done / rest over / skip / target reached (Alert) | ALERT_750MS_100 | ALERT_750MS_100 |
  | saved | STRONG_CLICK_100 | MEDIUM_CLICK_1_100 |
  | streak 5 | DOUBLE_CLICK_100 | SHORT_DOUBLE_SHARP_TICK_1_100 |
  | streak 10, 20, 30 … | 3× STRONG_CLICK_100 | 3× MEDIUM_CLICK_1_100 |

  Off = no vibration at all. **One haptic per shot**: when a shot ends a step / the workout or reaches the open
  target, the Alert replaces the make/miss/streak haptic. Streak = trailing makes (`currentStreak()`, undo
  recomputes it); a made shot at streak 5 plays streak 5 instead of make, at 10, 20, 30 … streak 10.
- Streak toast: Active shows "N in a row!" (2 s) when a live snapshot's `streak` rises to 5 or a multiple of 10;
  a toast already showing (undo, hold hint, step done) stays.
- Open target (setting Off / 25 / 50 / 100 / 200 shots; open sessions only): Active's ring shows session
  attempts / target, coloured by the session percentage, instead of the spot percentage; the shot that reaches
  it plays the Alert + backlight once and Active shows "Target reached" (2 s).
- No exit mid-session: leaving only via Pause (Resume / End & save / Discard; Discard asks twice within 3 s;
  BACK = resume). BACK on Home during a session goes to Pause.
- Crash resume: a restored session is Paused; Home shows "Resume session" first (selected) and an amber
  "Session in progress" line under the header; Resume opens Pause.
- One session at a time: Open Session / Workouts still open while one is in progress, but the picker's SELECT
  and the preview's START show a 2 s "Session in progress" toast instead of starting. Active falls back to
  Pause / Home if no live snapshot arrives within 1.5 s of entry.
- End & save of a session with no shots = discard (service sends SAVED{0}; Home toast "Nothing to save").
  SAVED{0} otherwise = save failed (Home toast "Save failed"; current.bin is kept). No SAVED within 3 s:
  Pause/Rest give the keys back with a "No reply" toast.
- Workout step done → long buzz → Rest (countdown ring, UP +15 s, SELECT skip); zero-rest steps show a 1.5 s
  toast instead. After the last step Rest shows the workout-done summary (UP keep shooting = extra shots).
- Step builder: fields Spot / Goal type / Value / Rest; SELECT on Spot opens the full spot picker; after Rest a
  mini-menu Add step / Save workout / Next step / Delete step / Delete workout (asked twice). Saves time out
  after 3 s with "No reply". A new workout's first step starts from the Settings default step (goal type, value,
  rest); "Add step" copies the current step. The value lists are shared with Settings (`StepValues.hpp`).
- Spot picker footer: "Last 40 % · best 46 %" from the index's per-spot records (GET_SPOT_STATS on show); just
  "Last 40 %" without a best (best needs ≥ `kMinAttemptsForRank` = 5 attempts at the spot in one session);
  hidden for a spot never shot.
- Settings (Home's Settings row → `ScreenId::Settings`; header "SETTINGS"; two-line list, the selected row shows
  its value; UP/DOWN move, **SELECT = next value** (cycles, wraps; sent at once as SET_SETTINGS), BACK = Home).
  Until the service's SETTINGS is in (GET_SETTINGS on show) the setting rows read "Loading…" and SELECT does
  nothing, so defaults never overwrite `settings.bin`.
  Rows: Goal type (Attempts · Makes · Time) · Goal value (5–50 "10 shots" / "10 makes", Time 30–180 "60 s"; a
  type change snaps the value) · Rest (0 / 15 / 30 / 60 s) · Open target (Off · 25 / 50 / 100 / 200 shots) ·
  Hold DOWN (Change spot · Pause) · Haptics (Off · Light · Strong) · Backlight on shot (On · Off) · Heart rate
  (On · Off; off = the HR sensor is never connected) · Colour scheme (Dark · Light) · CSV export (On · Off) ·
  Clear history ("N sessions" / "1 session", "Nothing to clear", "Loading…" before the first HISTORY page;
  first SELECT → "SELECT again to confirm" for 3 s, second SELECT → CLEAR_HISTORY, toast "History cleared",
  "0 sessions") · Restore workouts ("Deletes N custom", "No custom workouts", "Not while running" while a

  screen asks again (re-entering History). A full History takes 1 + 10 round trips (~1.1 s at 100 ms frames).

  running) is 11 messages and evicts item 0. The Model tracks the indices received (bitmask): a list with a
  gap is never marked loaded; it asks once more at once (past the 1 s guard; the reply lands a frame later,
  away from the snapshot) and raises `onWorkouts()` only when all items are in. A second loss gives up until
  a screen asks again (the waiting screen stays on "Loading…"; re-enter it).
- `appVersion` in the store manifest is the `.uapp` version verbatim, git suffix included (`0.0.0-dev`,
  `X.Y.Z-<n>-<hash>`): package from a commit tagged `apps-vX.Y.Z`.
